# RAPPORT FINAL ABSOLU + LES 6 CLARIFICATIONS + CORRECTIONS V2

## BEBBA Healthy Food

### « Vos Plats santé en un clic »

---

# 1. OBJET DU CAHIER DES CHARGES

Le présent document constitue le cahier des charges fonctionnel, métier et technique de référence pour la conception, le développement, les tests, le déploiement et l'exploitation de BEBBA Healthy Food.

Il consolide les exigences issues des cahiers des charges précédents, les clarifications définitivement décidées et les corrections ajoutées lors des dernières révisions.

Toute formulation antérieure contradictoire avec le présent document est remplacée par la règle définie ici.

---

# 2. PRINCIPES MÉTIER FONDAMENTAUX

* Les plats sont préparés après commande.
* Aucun plat ne doit être considéré comme préparé à l'avance.
* Le paiement de la V1 est effectué à la livraison par paiement à la livraison (COD).
* La livraison et l'encaissement sont deux opérations distinctes.
* Une commande livrée n'est donc pas automatiquement considérée comme encaissée.
* Le système doit conserver séparément l'état de livraison et l'état d'encaissement.
* Le Super Administrateur dispose de l'accès absolu prévu par le présent cahier.
* Toutes les opérations sensibles doivent être traçables.
* Les contrôles d'autorisation doivent être appliqués côté interface et côté serveur.

---

Le slogan officiel est exactement :

**« Vos Plats santé en un clic »**

# 7. IDENTIFICATION CLIENT PAR TÉLÉPHONE

L'identifiant client est construit à partir du numéro de téléphone international complet.

Le format de référence recommandé est :

`00 + indicatif pays + numéro national`

sans :

* signe `+` ;
* espace ;
* séparateur.

Exemple :

`+216 98123456`

devient :

`0021698123456`

Le client ne choisit pas son identifiant.

Un même numéro international normalisé ne peut correspondre qu'à un seul client.

# 11. ACTIONS PRODUIT — COMMANDER ET PERSONNALISER

Chaque produit présenté dans le menu doit afficher explicitement :

* **« Commander »**
* **« Personnaliser »**

Les deux actions sont distinctes mais doivent utiliser le même système de personnalisation.

## 11.1 Bouton « Personnaliser »

Lorsque le client clique sur **« Personnaliser »** :

1. la fenêtre/interface de personnalisation s'ouvre ;
2. les options autorisées sont affichées ;
3. le client sélectionne ses choix ;
4. les éventuels suppléments payants sont affichés ;
5. le prix est recalculé ;
6. le client peut ajouter le produit personnalisé au panier.

## 11.2 Bouton « Commander »

Lorsque le client clique sur **« Commander »**, une fenêtre de commande doit s'ouvrir.

**Le produit n'est pas considéré comme définitivement confirmé immédiatement.**

Cette fenêtre doit également permettre au client de :

* conserver le produit tel quel ;
* personnaliser le produit ;
* ajouter ou retirer les options autorisées ;
* sélectionner les suppléments disponibles ;
* voir le prix recalculé ;
* confirmer ensuite.

Le parcours est donc :

**Menu → Commander → Fenêtre de commande → Personnalisation éventuelle → Vérification → Confirmation**

## 11.3 Cohérence des deux parcours

Les deux parcours doivent aboutir au même mécanisme :

**Menu → Personnaliser → Personnalisation → Panier**

ou :

**Menu → Commander → Fenêtre de commande → Personnalisation éventuelle → Panier/confirmation**

Il ne doit pas exister deux systèmes de personnalisation différents.

# 13. PANIER

Le panier doit :

* conserver les produits ;

Deux produits identiques avec des personnalisations différentes doivent pouvoir être distingués.

# 14. STATUTS DES COMMANDES

Les statuts officiels des commandes sont exclusivement :

`received`

`preparing`

`ready`

`waiting_for_driver`

`delivering`

`delivered`

`cancelled`

La casse est obligatoire.

---

# 15. RÉFÉRENCE UNIQUE DES STATUTS

Les statuts précédents constituent la référence unique pour les commandes.

Les anciennes formulations :

* `RECEIVED` ;
* `Reçue` ;
* ou toute autre variation

ne doivent pas être utilisées comme valeurs officielles.

---

# 16. CYCLE DE COMMANDE

Le cycle nominal est :

`received → preparing → ready → waiting_for_driver → delivering → delivered`

Une commande peut également passer à :

`cancelled`

selon les règles de cancellation applicables.

---

# 17. PAIEMENT COD

La V1 utilise le paiement à la livraison.

Le système doit distinguer :

* montant à encaisser ;
* montant encaissé ;
* statut d'encaissement.

Les statuts de paiement sont :

`to_collect`

et

`paid`

Une livraison réussie ne modifie pas automatiquement le statut de paiement.

---

# 18. LIVRAISON ET ENCAISSEMENT

La livraison et l'encaissement sont indépendants.

Le système doit pouvoir représenter notamment :

* livré / non encaissé ;
* livré / encaissé ;
* non livré / non encaissé.

Le Super Administrateur doit pouvoir intervenir lorsque le livreur ne peut pas finaliser une opération autorisée.

---

# 19. NUMÉRO OFFICIEL DE COMMANDE

Chaque commande doit posséder un identifiant/numéro officiel permettant :

* l'identification ;
* le suivi ;
* la recherche ;
* la communication avec le client ;
* la traçabilité ;
* le rapprochement avec les opérations associées.

---

# 20. TRACKING

Chaque commande suivable doit disposer d'un `trackingToken` de 8 caractères.

La clé locale de référence est :

`bebba_last_tracking_token`

Le fallback de démonstration est :

`tk_bebba_1047_demo`

Lorsque `?token=` est fourni, il doit être prioritaire selon les règles de tracking.

---

# 21. CUISINE / KDS

La cuisine doit pouvoir :

* consulter les commandes reçues ;
* voir les commandes à préparer ;
* démarrer la préparation ;
* terminer la préparation ;
* faire progresser la commande selon la machine d'état ;
* voir les informations nécessaires à la production.

Lorsque la cuisine passe une commande à **« En préparation »**, la consommation du stock définie au point #10 est déclenchée.

---

# 22. CONSOMMATION DU STOCK — RÈGLE DÉFINITIVE #10

Le stock est consommé **au moment exact où la cuisine clique sur « En préparation »**.

La transition :

`received → preparing`

déclenche la consommation correspondant à la commande.

La consommation :

* ne doit être effectuée qu'une seule fois ;
* doit être transactionnelle ;
* doit être idempotente ;
* doit être traçable ;
* ne doit pas être répétée lors d'une répétition de requête.

Aucun autre moment ne doit provoquer une seconde consommation pour la même opération.

---

# 23. INGREDIENTS

Le système doit permettre de gérer les ingrédients, leurs unités, coûts, seuils, stocks, mouvements et relations avec les recettes.

---

# 24. INGREDIENTS — MODE READ ONLY

Un utilisateur disposant uniquement de la permission **READ ONLY** peut consulter les informations autorisées concernant les ingrédients.

Il peut notamment :

* voir la liste ;
* rechercher ;
* consulter le détail ;
* consulter l'unité ;
* consulter le coût lorsque son rôle l'autorise ;
* consulter le stock lorsque son rôle l'autorise ;
* consulter le seuil d'alerte lorsque son rôle l'autorise.

Il ne peut pas :

* ajouter ;
* modifier ;
* supprimer ;
* modifier le coût ;
* modifier l'unité ;
* modifier le seuil ;
* modifier les données de l'ingrédient ;
* effectuer un mouvement de stock ;
* effectuer un réapprovisionnement ;
* modifier ou supprimer l'historique.

Le mode `READ ONLY` doit être appliqué :

* dans l'interface ;
* dans les permissions ;
* côté API ;
* côté serveur.

Masquer un bouton ne constitue pas une mesure de sécurité suffisante.

---

# 30. LIVREURS — GESTION

* réactiver un livreur ;

* consulter son activité ;
* l'affecter à une commande ;
* le réaffecter.

# 31. DÉSACTIVATION D'UN LIVREUR

La désactivation :

* ne supprime pas le livreur ;
* conserve son historique ;
* empêche son utilisation lorsque les règles métier l'interdisent ;
* permet une réactivation ultérieure.

La désactivation est différente de la suppression.

---

# 32. SUPPRESSION / ARCHIVAGE D'UN LIVREUR

La suppression physique ne doit pas détruire les informations historiques nécessaires :

* aux commandes ;
* aux livraisons ;
* aux encaissements ;
* aux statistiques ;
* aux audits.

Lorsque la conservation historique est nécessaire, l'archivage ou la désactivation doit être privilégié.

---

# 33. AFFECTATION DES LIVREURS

L'administration doit pouvoir :

* affecter un livreur ;
* réaffecter un livreur ;
* consulter le livreur affecté ;
* conserver la trace de l'affectation.

L'identifiant du livreur affecté doit être conservé de manière cohérente.

---

# 34. GPS DU LIVREUR — RÈGLE DÉFINITIVE #12

Pendant l'état :

`delivering`

la position du livreur est transmise **toutes les 10 secondes**.

Aucune position fictive ne doit être générée lorsque la transmission est interrompue.

---

# 35. HISTORIQUE GPS — RÈGLE DÉFINITIVE #13

L'historique des positions GPS est conservé pendant **72 heures**.

Les données doivent être protégées contre les accès non autorisés.

À expiration de la durée de conservation, elles doivent être supprimées ou anonymisées conformément à la politique applicable.

# 36. RÉCLAMATIONS

`OPEN`

`IN_REVIEW`

`CLOSED`

# 37. CRÉATION D'UNE RÉCLAMATION — RÈGLE DÉFINITIVE #15

Une réclamation peut être créée jusqu'à **3 heures après la confirmation de la livraison**.

Le serveur constitue la référence temporelle.

Toute tentative hors délai doit être refusée.

---

# 38. NOMBRE DE RÉCLAMATIONS — RÈGLE DÉFINITIVE #16

Une commande peut avoir **une seule réclamation**.

Une deuxième création doit être refusée.

Le contrôle doit être effectué côté serveur et doit résister aux créations concurrentes.

# 39. CHAT

Le chat est exclusivement associé à une réclamation.

# 40. PHOTOS DE RÉCLAMATION

# 42. PROMOTIONS — RÈGLE DÉFINITIVE #11

Lorsque plusieurs promotions/avantages sont applicables et autorisés au cumul, ils sont appliqués dans l'ordre suivant :

**la promotion la plus récente en premier, puis celle qui la précède, puis la suivante, etc.**

L'ordre doit être déterministe.

Les promotions non applicables ou exclues par leurs conditions ne sont pas appliquées.

Le résultat du calcul doit être conservé dans la commande.
